# Архитектура

## 1. Общая концепция

Приложение реализуется как **модульный монолит**.

Главная архитектурная идея:

> Простая архитектура сейчас, чёткие границы для возможного разделения потом.

MVP не требует микросервисной архитектуры или сложной инфраструктуры.

Frontend и backend логически разделены и развёртываются как два сервиса внутри
одного `docker compose`:

- `frontend` — nginx: раздаёт собранное приложение и проксирует `/api` на backend;
- `backend` — Go: HTTP API.

Наружу публикуется только frontend (nginx), поэтому браузер работает с единой
точкой входа без CORS.

---

## 2. Целевая структура

В MVP:

```text
Browser
├── Frontend
└── Local progress
        │
       HTTP
        │
        ▼
Go application
├── HTTP/API
├── Application
├── Domain
└── Storage
        │
        ▼
    JSON files
```

Frontend и backend — отдельные сервисы в одном `docker compose`:

```text
Browser (http://localhost:8080)
    │
    ▼
Frontend (nginx)
  ├── Static assets (dist)
  └── proxy /api → backend
        │
       HTTP
        │
        ▼
Go application (backend)
├── HTTP/API
├── Application
├── Domain
└── Storage
        │
        ▼
    JSON files
```

Наружу публикуется только frontend (nginx); backend наружу не публикуется и
достигается через docker network. Такое разделение позволяет в будущем развернуть
frontend и backend независимо (например, фронт на CDN, а не в nginx-контейнере).

## 3. Архитектурные принципы

### AR-01. Модульный монолит (один compose, два процесса)

По коду приложение остаётся модульным монолитом и развёртывается одним
`docker compose`. В runtime задействованы два процесса одного проекта:
frontend (nginx) и backend (Go). Это цельное приложение, а не микросервисы;
дополнительные сервисы (БД, Redis и т.п.) в MVP не вводятся.

### AR-02. Простота важнее абстракций

Не вводить архитектурные конструкции без конкретной необходимости.

Предпочтение:

- стандартной библиотеке;
- простым структурам данных;
- небольшим функциям;
- явным зависимостям;
- понятному control flow.

### AR-03. HTTP является границей frontend/backend

Frontend не должен зависеть от внутренней реализации Go backend.

Даже в одном контейнере frontend должен взаимодействовать с backend через HTTP API.

### AR-04. JSON вместо базы данных

Puzzle data хранится в обычных JSON-файлах.

База данных не используется в MVP.

### AR-05. Storage изолирован

Application/domain logic не должны напрямую работать с файловой системой.

Знание о:

- директориях;
- именах файлов;
- JSON encoding;
- способе загрузки данных

должно находиться в storage/infrastructure layer.

### AR-06. Domain не зависит от инфраструктуры

Domain logic не должен зависеть от:

- HTTP;
- filesystem;
- JSON storage;
- frontend.

### AR-07. Stateless backend

Backend не должен хранить пользовательский игровой прогресс в MVP.

Puzzle data является практически read-only.

### AR-08. Progress хранится на клиенте

Незавершённое решение хранится в браузере.

Backend не должен вводить user accounts или sessions только ради сохранения прогресса.

### AR-09. API должен быть отделяемым

API должен быть пригоден для того, чтобы frontend впоследствии запускался отдельно.

Для MVP достаточно `/api/v1`.

### AR-10. Breaking changes допустимы

Frontend и backend выпускаются вместе.

Не требуется поддерживать старые версии API в MVP.

### AR-11. Один Docker Compose

Весь проект должен запускаться через:

```text
docker compose up
```

### AR-12. Минимум runtime infrastructure

MVP не должен требовать:

- database container;
- Redis;
- message broker;
- API gateway;
- service mesh;
- Kubernetes.

## 4. Backend

Backend реализуется на Go.

Предпочтительно использовать стандартную библиотеку.

Основные компоненты:

```text
HTTP
 │
 ▼
Application
 │
 ├── Domain
 │
 └── Storage interface
          │
          ▼
      JSON storage
```

## 5. Domain

Domain содержит предметную логику:

- Puzzle;
- GameState;
- состояния клеток;
- работу с подсказками;
- проверку решения;
- связанные правила.

Domain не должен знать, откуда пришли данные.

Например, domain не должен открывать:

```text
data/puzzles/001.json
```

## 6. Application

Application layer отвечает за use cases.

Примеры:

- получение списка кроссвордов;
- получение кроссворда;
- проверка решения;
- другие прикладные операции.

Application координирует domain и infrastructure.

HTTP handlers не должны реализовывать application logic самостоятельно.

## 7. Storage

Storage отвечает за получение puzzle data.

Для MVP реализация основана на JSON-файлах.

Пример:

```text
data/
└── puzzles/
    ├── 001.json
    ├── 002.json
    └── ...
```

Если application зависит от интерфейса repository, интерфейс должен быть небольшим и отражать реальные use cases.

Например:

```go
type PuzzleRepository interface {
	Get(ctx context.Context, id string) (*Puzzle, error)
	List(ctx context.Context) ([]Puzzle, error)
}
```

Не следует создавать generic repository abstraction без конкретной необходимости.

## 8. Puzzle format

Каждый puzzle должен иметь версию формата.

Пример:

```json
{
  "version": 1,
  "id": "001",
  "width": 10,
  "height": 10,
  "difficulty": "medium",
  "rowHints": [],
  "columnHints": [],
  "solution": []
}
```

При загрузке необходимо проверять:

- корректность JSON;
- допустимость размеров;
- соответствие размеров solution;
- корректность hints;
- наличие обязательных полей.

Puzzle files не изменяются во время обычной игры.

## 9. HTTP API

API имеет namespace:

```text
/api/v1/
```

Примеры:

```text
GET /api/v1/puzzles
GET /api/v1/puzzles/{id}
```

HTTP handlers должны быть тонкими.

Их ответственность:

1. получить request;
2. провалидировать входные данные;
3. вызвать application layer;
4. преобразовать результат в HTTP response.

Handler не должен:

- читать JSON-файлы напрямую;
- реализовывать domain logic;
- знать структуру директорий storage.

## 10. HTTP DTOs

API contract не обязан совпадать с domain model.

При необходимости используются отдельные request/response DTO.

Это позволяет менять внутреннюю модель без автоматического изменения API.

## 11. Frontend

Frontend является отдельным логическим модулем.

Он отвечает за:

- отображение puzzle;
- пользовательские взаимодействия;
- состояние текущей игры;
- local progress;
- таймер;
- mobile UX.

Frontend не должен знать:

- где лежат JSON-файлы;
- как backend читает puzzle;
- внутренние Go types.

## 12. Game state

Puzzle definition и пользовательский game state — разные сущности.

Концептуально:

```text
Puzzle definition
      │
      ▼
Game state
      │
      ▼
Domain/game logic
      │
      ▼
UI
```

UI отображает состояние, но не должен быть единственным источником истины для domain rules.

## 13. Mobile

20×20 является штатным размером.

Архитектура frontend не должна предполагать, что игровое поле всегда помещается на экране без адаптации.

Interaction должен поддерживать touch.

Не следует строить UX вокруг hover или mouse-only interactions.

## 14. Docker

Проект развёртывается одним `docker compose` с двумя сервисами:

```text
backend (Go API)          frontend (nginx)
   /api/v1/*                  static assets + proxy /api -> backend
        └────────────────────────────┘
```

- **backend** — multi-stage build (golang → minimal alpine); наружу не публикуется.
- **frontend** — multi-stage build: Vite собирает `dist` (node stage), затем nginx
  раздаёт статику и проксирует `/api` на backend.

Из браузера наружу публикуется только nginx (порт 8080), поэтому используется
единая точка входа без CORS. В runtime не должны попадать инструменты разработки,
если они не нужны для запуска.

## 15. Configuration

Конфигурация должна быть минимальной.

Допустимые параметры:

- listen address;
- data directory;
- logging level.

Конфигурация передаётся через environment variables.

Должны существовать разумные defaults.

## 16. Logging

Использовать стандартный structured logging Go там, где это удобно.

Логировать:

- запуск приложения;
- ошибки конфигурации;
- проблемы загрузки puzzle;
- неожиданные ошибки application/API.

Не логировать каждый ход пользователя.

## 17. Testing

Наиболее важные тесты:

- domain logic;
- puzzle validation;
- puzzle loading;
- clue calculations;
- game state transitions;
- API behavior.

Тесты должны быть быстрыми и детерминированными.

Для Go предпочтительны table-driven tests там, где они делают набор сценариев понятнее.

## 18. Dependency policy

Новые зависимости добавляются только при наличии реальной необходимости.

Перед добавлением dependency проверить:

1. можно ли решить задачу стандартной библиотекой;
2. насколько dependency действительно упрощает решение;
3. не создаёт ли она лишнюю архитектурную связанность.

Не добавлять dependency ради небольшого удобства.

## 19. Evolution

Архитектура должна позволять заменить storage в будущем:

```text
Application
    │
    ▼
PuzzleRepository
    │
    ├── JSON files
    │
    └── Future database
```

Однако реализация database storage не является частью MVP.

Аналогично frontend должен иметь возможность быть вынесенным в отдельный deployable unit:

```text
Frontend
   │
  HTTP
   │
Backend API
```

Но отдельный frontend container/CDN не является обязательным для MVP.

## 20. Что намеренно не делаем

До появления конкретной потребности не добавляем:

- database;
- authentication;
- user accounts;
- Redis;
- queues;
- microservices;
- event sourcing;
- CQRS;
- generic repository frameworks;
- dependency injection frameworks;
- distributed tracing;
- сложный caching layer;
- API gateway.

Главный критерий:

Не реализовывать будущую систему вместо текущего продукта.
