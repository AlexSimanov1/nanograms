# Архитектурные требования

## 1. Общие принципы

Проект представляет собой **модульный монолит** с минимальным количеством инфраструктуры.

Основные цели:

- простота разработки и локального запуска;
- отсутствие БД в MVP;
- backend на Go;
- единый deployment через Docker Compose;
- чёткое разделение frontend и backend на уровне логических модулей;
- возможность в будущем разделить frontend и backend без переписывания domain/application логики;
- отсутствие преждевременной сложности.

> **Простая архитектура сейчас, чёткие границы для возможного разделения потом.**

---

## 2. Архитектурный стиль

### AR-01. Модульный монолит

Приложение должно быть единым deployable unit.

Внутри монолита логически разделяются:

- HTTP/API слой;
- application/service слой;
- domain/model слой;
- persistence/storage слой;
- frontend/static assets.

```text
                    ┌───────────────────────┐
                    │       Go backend      │
                    │                       │
Browser ───────────►│  HTTP/API             │
                    │      ↓                │
                    │  Application          │
                    │      ↓                │
                    │  Domain               │
                    │      ↓                │
                    │  File Storage         │
                    │                       │
                    │  Static frontend      │
                    └───────────────────────┘
                              │
                              ▼
                         JSON files
```

Микросервисы в MVP не используются.

---

## 3. Backend

### AR-02. Backend на Go

Backend реализуется на Go.

Предпочтительно использовать стандартную библиотеку и небольшое количество зависимостей:

- `net/http`;
- `encoding/json`;
- `context`;
- стандартное логирование или лёгкую библиотеку.

Тяжёлый web framework не требуется, если он не решает конкретную проблему проекта.

### AR-03. Backend не зависит от frontend

Граница между frontend и backend проходит через HTTP API:

```text
Frontend
    │
    │ HTTP
    ▼
API handlers
    │
    ▼
Application services
    │
    ▼
Domain
    │
    ▼
Storage
```

Даже если frontend на первом этапе раздаётся тем же Go-процессом, он считается отдельным логическим модулем.

---

## 4. Хранение данных

### AR-04. База данных не используется в MVP

SQL/NoSQL database не является частью MVP.

Данные хранятся в обычных файлах, основной формат — JSON.

```text
data/
└── puzzles/
    ├── puzzle-001.json
    ├── puzzle-002.json
    └── puzzle-003.json
```

Это сознательное архитектурное решение, соответствующее масштабу пет-проекта.

### AR-05. Storage изолирован за интерфейсом

Application/domain код не должен знать о конкретном способе хранения.

```go
type PuzzleRepository interface {
    Get(ctx context.Context, id string) (*Puzzle, error)
    List(ctx context.Context) ([]Puzzle, error)
}
```

Конкретная реализация:

```text
PuzzleRepository
       ▲
       │
JSONPuzzleRepository
       │
       ▼
   *.json files
```

Это позволяет в будущем заменить JSON на PostgreSQL без переписывания domain/application логики.

Не следует создавать абстракции без реальной необходимости. Основная граница абстракции — persistence.

---

## 5. Файлы кроссвордов

### AR-06. Контент отделён от кода

Кроссворды не должны быть захардкожены в Go-коде.

```text
/app
├── cmd/
├── internal/
└── data/
    └── puzzles/
        ├── 001.json
        ├── 002.json
        └── 003.json
```

Добавление нового кроссворда не должно требовать изменения backend-кода.

### AR-07. Формат JSON версионируется

JSON-файл кроссворда должен содержать версию формата.

```json
{
  "version": 1,
  "id": "001",
  "width": 10,
  "height": 10,
  "difficulty": "medium",
  "rowHints": [],
  "columnHints": [],
  "solution": []
}
```

Полноценная система миграций для MVP не требуется.

---

## 6. Состояние пользователя

### AR-08. Server-side user state не требуется в MVP

Поскольку аккаунтов нет, прогресс пользователя хранится на стороне браузера.

```text
Browser
└── localStorage / IndexedDB
    └── PuzzleProgress
```

Backend хранит преимущественно неизменяемый контент кроссвордов.

В будущем server-side progress может быть добавлен вместе с аккаунтами и синхронизацией.

---

## 7. HTTP API

### AR-09. Backend предоставляет явный HTTP API

Даже внутри монолита frontend взаимодействует с backend через HTTP API.

Минимальный API MVP:

```text
GET /api/puzzles
GET /api/puzzles/{id}
```

В дальнейшем API может расширяться:

```text
POST /api/progress
GET  /api/progress
POST /api/puzzles/{id}/check
```

### AR-10. API отделён от внутренних моделей

HTTP DTO не должны автоматически становиться domain-моделями.

```text
HTTP request/response
        ↓
       DTO
        ↓
Application service
        ↓
      Domain
```

Это позволяет независимо изменять внутреннюю модель и HTTP API.

---

## 8. Frontend

### AR-11. Frontend является отдельным логическим модулем

Frontend должен находиться отдельно от Go backend с точки зрения исходного кода.

```text
frontend/
├── src/
├── package.json
└── ...
```

После сборки frontend превращается в статические assets:

```text
static/
├── index.html
├── assets/
└── ...
```

На первом этапе эти assets раздаются Go-сервером.

### AR-12. Frontend потенциально deployable отдельно

Frontend взаимодействует с backend через HTTP API и не должен зависеть от того, что его обслуживает именно Go-процесс.

В будущем возможна схема:

```text
┌─────────────────┐       ┌─────────────────┐
│ Frontend        │ HTTP  │ Go backend      │
│ CDN/container   │──────►│ container       │
└─────────────────┘       └────────┬────────┘
                                   │
                                   ▼
                                storage
```

Разделение должно быть deployment concern, а не поводом переписывать domain/application код.

---

## 9. Docker и запуск

### AR-13. Весь проект запускается через Docker Compose

Developer experience должен сводиться к:

```bash
docker compose up
```

После этого доступны frontend, backend и файлы данных.

Не должно требоваться вручную запускать отдельные компоненты.

### AR-14. MVP — один runtime container

В MVP не требуются отдельные runtime-контейнеры для API, frontend, database, Redis, message broker или reverse proxy.

Предпочтительная схема:

```text
Docker build

Frontend build
      ↓
Frontend assets
      ↓
Go build
      ↓
Single runtime image
      ↓
Go server
 ├── /api/*
 └── /*
```

---

## 10. Возможность будущего разделения

### AR-15. Frontend и backend должны разделяться без изменения domain logic

Текущая схема:

```text
┌──────────────────────────────┐
│         Go container         │
│                              │
│ frontend ──► HTTP API        │
│                 │            │
│                 ▼            │
│             application      │
└──────────────────────────────┘
```

Будущая схема:

```text
┌─────────────────┐       ┌─────────────────┐
│ Frontend        │ HTTP  │ Go backend      │
│ container/CDN   │──────►│ container       │
└─────────────────┘       └────────┬────────┘
                                   │
                                   ▼
                                storage
```

Разделение должно быть возможным за счёт изменения deployment configuration, а не переписывания бизнес-логики.

---

## 11. Граница совместимости

### AR-16. API имеет явную версию

API рекомендуется размещать под версией:

```text
/api/v1/...
```

В MVP:

- не требуется поддерживать несколько API-версий;
- breaking changes допустимы;
- frontend и backend могут изменяться одновременно;
- изменение API сопровождается изменением frontend.

Версионирование нужно прежде всего для явной границы между frontend и backend.

Если в будущем компоненты начнут деплоиться независимо, можно будет ввести полноценные правила backwards compatibility.

---

## 12. Архитектурные границы

В MVP достаточно обеспечить три основные границы:

### 1. Frontend ↔ HTTP API

```text
Frontend
   │
  HTTP
   │
   ▼
Backend
```

### 2. Application ↔ Storage

```text
Application
    │
Repository interface
    │
    ▼
JSON storage
```

### 3. Application/Domain ↔ Infrastructure

Бизнес-логика не должна зависеть от конкретной инфраструктуры.

---

## 13. Что не следует добавлять преждевременно

Не требуются:

- микросервисы;
- generic repository framework;
- DI-контейнер;
- event bus;
- CQRS;
- сложная domain-driven architecture;
- database abstraction framework;
- message broker;
- Redis;
- отдельный API gateway;
- service mesh.

Основная цель — не максимальная архитектурная универсальность, а **простая система с хорошо проведёнными границами**.

## Ключевой принцип

> **Простая архитектура сейчас, чёткие границы для возможного разделения потом.**

Нужно сознательно избегать преждевременной абстракции. Достаточно хорошо провести границы **Frontend ↔ HTTP API**, **Application ↔ Storage** и **Application/Domain ↔ Infrastructure**.
