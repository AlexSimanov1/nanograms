# Product Requirements Document: Nanograms

## 1. Описание продукта

Nanograms — небольшой веб-сервис для решения японских кроссвордов (нанограмм).

Основной пользовательский сценарий:


1. пользователь открывает каталог;

2. выбирает кроссворд;

3. начинает решение;

4. отмечает клетки;

5. получает обратную связь о текущем решении;

6. завершает кроссворд;

7. при необходимости возвращается к незавершённому кроссворду.

Основной фокус продукта — удобный и приятный процесс решения.

Проект является pet-проектом, поэтому MVP должен оставаться небольшим и не требовать сложной инфраструктуры.

---

# 2. Цели

## 2.1. Основная цель

Сделать удобный веб-интерфейс, в котором можно быстро открыть японский кроссворд и комфортно решить его как на компьютере, так и на телефоне.

## 2.2. Цели MVP

MVP должен позволять:

- просматривать доступные кроссворды;

- выбирать кроссворд;

- решать кроссворд;

- отмечать заполненные и пустые клетки;

- исправлять ошибки;

- видеть прогресс;

- сохранить незавершённое решение;

- продолжить решение после перезагрузки страницы;

- завершить кроссворд;

- видеть время решения.

---

# 3. Не входит в MVP

Следующие возможности сознательно не входят в MVP:

- регистрация пользователей;

- авторизация;

- серверные аккаунты;

- синхронизация прогресса между устройствами;

- социальные функции;

- комментарии;

- рейтинги;

- достижения;

- генератор кроссвордов;

- редактор кроссвордов;

- онлайн-соревнования;

- multiplayer;

- сложная статистика;

- платные функции.

Если для реализации MVP возникает необходимость в одной из этих возможностей, сначала необходимо пересмотреть требование, а не автоматически добавлять её.

---

# 4. Пользовательские сценарии

## US-01. Просмотр каталога

Как пользователь, я хочу увидеть список доступных кроссвордов, чтобы выбрать тот, который хочу решить.

### Acceptance criteria

- пользователь может открыть каталог;

- каталог содержит список доступных кроссвордов;

- для кроссворда отображается как минимум его название/идентификатор и размер;

- пользователь может открыть выбранный кроссворд.

---

## US-02. Начало решения

Как пользователь, я хочу открыть кроссворд и сразу начать решать его.

### Acceptance criteria

- поле кроссворда отображается полностью;

- отображаются подсказки строк;

- отображаются подсказки столбцов;

- текущий прогресс изначально пустой, если сохранённого прогресса нет;

- интерфейс пригоден для использования на мобильном устройстве.

---

## US-03. Заполнение клетки

Как пользователь, я хочу отметить клетку как заполненную.

### Acceptance criteria

- пользователь может изменить состояние клетки;

- изменение происходит без перезагрузки страницы;

- состояние клетки визуально понятно.

---

## US-04. Отметка пустой клетки

Как пользователь, я хочу отметить клетку как заведомо пустую.

### Acceptance criteria

- пользователь может установить состояние `cross`;

- состояние визуально отличается от заполненной клетки;

- пользователь может удалить отметку.

---

## US-05. Исправление решения

Как пользователь, я хочу легко исправлять свои действия.

### Acceptance criteria

- любую клетку можно изменить;

- любую клетку можно очистить;

- исправление не требует перезагрузки страницы.

---

## US-06. Сохранение прогресса

Как пользователь, я хочу закрыть страницу и продолжить решение позже.

### Acceptance criteria

- незавершённый прогресс сохраняется в браузере;

- после перезагрузки страницы прогресс восстанавливается;

- прогресс одного кроссворда не смешивается с прогрессом другого.

---

## US-07. Таймер

Как пользователь, я хочу видеть, сколько времени потратил на решение.

### Acceptance criteria

- таймер отображается во время решения;

- таймер не сбрасывается при обычном изменении клеток;

- сохранённый незавершённый кроссворд сохраняет состояние таймера;

- после завершения кроссворда время фиксируется.

---

## US-08. Завершение кроссворда

Как пользователь, я хочу понять, что решил кроссворд правильно.

### Acceptance criteria

- приложение может определить соответствие текущего решения эталонному;

- при правильном решении пользователь получает понятное уведомление;

- время решения отображается после завершения.

---

# 5. Игровое поле

## 5.1. Размеры

MVP должен поддерживать кроссворды размером до 20×20.

Размер 20×20 считается штатным сценарием, а не edge case.

## 5.2. Клетки

Каждая клетка может находиться минимум в трёх состояниях:

- `empty`;

- `filled`;

- `cross`.

Начальное состояние — `empty`.

## 5.3. Подсказки

Для каждой строки и столбца отображаются соответствующие числовые подсказки.

Подсказки должны быть визуально связаны с соответствующей строкой или столбцом.

---

# 6. Mobile UX

Мобильная версия является частью MVP.

Интерфейс должен быть удобен как минимум на современных смартфонах.

Не следует рассчитывать на:

- hover;

- правую кнопку мыши;

- клавиатуру;

- большие экраны.

Основные действия должны быть доступны через touch interaction.

Предпочтительный вариант взаимодействия:

- tap по клетке;

- явный режим заполнения/крестика;

- возможность очистить клетку;

- drag interaction может использоваться, если он делает решение удобнее.

Сложные жесты не должны добавляться без необходимости.

---

# 7. Сохранение прогресса

В MVP прогресс пользователя хранится на стороне браузера.

Backend не хранит пользовательские сессии и прогресс.

Требования к client-side storage:

- данные должны переживать перезагрузку страницы;

- данные должны быть привязаны к конкретному puzzle ID;

- формат должен позволять в будущем изменить структуру сохранения;

- повреждённые данные не должны ломать загрузку приложения.

Конкретная технология хранения выбирается на этапе реализации.

---

# 8. Каталог

Каталог должен позволять получить список доступных кроссвордов.

Минимальная информация:

- ID;

- размер;

- название или другое человекочитаемое описание;

- сложность, если она предусмотрена данными.

Каталог не обязан иметь сложную систему фильтрации в MVP.

---

# 9. API

Frontend и backend взаимодействуют через HTTP API.

MVP использует API версии `v1`.

Основные endpoints:

```text
GET /api/v1/puzzles
GET /api/v1/puzzles/{id}
```

API отвечает за получение данных кроссвордов.

Проверка пользовательского решения может выполняться на клиенте, если это позволяет архитектура конкретной реализации.

# 10. Нефункциональные требования

## 10.1. Простота

MVP не должен требовать:

- базы данных;
- Redis;
- очередей;
- микросервисов;
- отдельного API gateway;
- сложной инфраструктуры.

## 10.2. Запуск

Проект должен запускаться одной командой:

docker compose up

## 10.3. Производительность

Кроссворды размером до 20×20 должны работать без заметных задержек при обычных действиях пользователя.

## 10.4. Надёжность

Перезагрузка страницы не должна приводить к потере сохранённого незавершённого прогресса.

# 11. Definition of Done

MVP считается готовым, когда:

- пользователь может открыть каталог;
- пользователь может выбрать кроссворд;
- кроссворд отображается корректно;
- пользователь может заполнять клетки;
- пользователь может отмечать пустые клетки;
- пользователь может очищать клетки;
- интерфейс работает на мобильном устройстве;
- прогресс сохраняется между перезагрузками;
- таймер работает;
- приложение определяет завершение кроссворда;
- backend предоставляет необходимые данные через HTTP API;
- кроссворды хранятся в JSON-файлах;
- приложение запускается через docker compose up;
- основные сценарии покрыты тестами.

# 12. Возможное развитие после MVP

После проверки MVP могут появиться:

- авторизация;
- серверное сохранение прогресса;
- синхронизация между устройствами;
- статистика;
- история решений;
- новые размеры;
- генератор кроссвордов;
- редактор;
- рейтинги;
- социальные возможности.

Эти возможности не должны влиять на архитектуру MVP без конкретной необходимости.
