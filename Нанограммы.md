# Product Requirements Document (PRD)

## Японские кроссворды — веб-приложение для решения нанограмм

**Статус:** Draft / MVP  

**Версия:** 0.1  

**Дата:** 23 августа 2026

---

## 1. Краткое описание

Небольшое веб-приложение для решения японских кроссвордов (нанограмм) непосредственно в браузере.

Основная идея продукта:

> **Открыл → выбрал → решаешь.**

Пользователь должен без регистрации и сложного onboarding быстро выбрать кроссворд, решить его на удобном игровом поле и получить результат.

Главный фокус проекта — не каталог, социальные функции или аккаунты, а **качество самого процесса решения**, в том числе на мобильных устройствах.

---

## 2. Видение продукта

### Продуктовое видение

Простой и приятный веб-сервис для людей, которые любят японские кроссворды и хотят решать их в браузере.

Приложение должно быть:

- быстрым;

- понятным без объяснений;

- удобным мышью, клавиатурой и touch;

- одинаково пригодным для коротких и более продолжительных сессий;

- ориентированным прежде всего на процесс решения.

### Основная гипотеза

Если пользователь может открыть сайт и начать решать кроссворд за несколько секунд, а само взаимодействие с полем ощущается удобным и надёжным, то сайт будет достаточно привлекательным для регулярного решения пазлов.

### Ключевой UX-принцип

**«Открыл → выбрал → решаешь».**

Не требовать регистрации, настройки профиля или прохождения длинного onboarding перед началом игры.

---

# 3. Цели проекта

## 3.1. Цели MVP

1. Реализовать полноценный процесс решения японского кроссворда в браузере.

2. Сделать удобный интерфейс как для desktop, так и для мобильных устройств.

3. Поддержать кроссворды как минимум до размера **20×20** без необходимости использовать zoom.

4. Обеспечить сохранение незавершённого прогресса.

5. Дать пользователю возможность проверить решение и получить результат.

6. Создать техническую основу, которую впоследствии можно расширять новыми размерами, кроссвордами и функциями.

## 3.2. Не является целью MVP

В MVP не требуется:

- регистрация и авторизация;

- синхронизация между устройствами;

- социальный граф;

- рейтинги и соревнования;

- комментарии и лайки;

- пользовательская генерация кроссвордов;

- генератор кроссвордов;

- мобильное приложение;

- монетизация;

- AI-функции;

- сложная система достижений.

---

# 4. Целевая аудитория

## Основная аудитория

Люди, которые уже знают правила японских кроссвордов и хотят решать их в браузере.

## Вторичная аудитория

- люди, которые впервые пробуют нанограммы;

- любители головоломок;

- пользователи, которым нужны короткие задачи на 5–15 минут;

- пользователи мобильных устройств.

Обучение правилам может присутствовать в будущем, но **не является центральной задачей MVP**.

# 5. Scope MVP

## 5.1. Входит в MVP

### Каталог кроссвордов

Пользователь может:

- увидеть доступные кроссворды;

- увидеть их размер;

- увидеть сложность;

- понять, решён ли кроссворд;

- продолжить начатый кроссворд.

Минимальные размеры:

- 5×5;

- 10×10;

- 15×15;

- 20×20.

### Игровое поле

Пользователь может:

- закрашивать клетки;

- ставить крестики/метки пустых клеток;

- очищать клетки;

- видеть подсказки строк;

- видеть подсказки столбцов;

- видеть текущий прогресс;

- сбрасывать решение.

### Проверка решения

Пользователь может запросить проверку текущего решения.

При правильном решении:

- показать состояние завершения;

- показать время решения;

- предложить перейти к следующему кроссворду.

При неправильном решении:

- сообщить, что решение содержит ошибки;

- не разрушать текущий прогресс.

### Сохранение прогресса

Незавершённый кроссворд сохраняется локально.

После перезагрузки страницы пользователь может продолжить решение с того же места.

### Таймер

Во время решения ведётся время.

Таймер:

- запускается при начале решения;

- продолжает корректно работать после восстановления прогресса;

- фиксирует итоговое время при завершении.

### Mobile UX

Приложение должно быть пригодно для touch-устройств.

Поддерживаются:

- portrait;

- landscape;

- tap;

- drag по последовательности клеток;

- переключение режима «закрасить / крестик».

**20×20 считается нормальным рабочим размером для мобильного устройства.**

Zoom/pan не является обязательным для MVP и может быть добавлен позже для больших размеров.

# 6. User Stories

## US-01 — Выбрать кроссворд

**Как пользователь**,  

я хочу увидеть доступные кроссворды и выбрать один,  

**чтобы начать решение.**

### Acceptance criteria

- Пользователь видит список доступных кроссвордов.

- Для каждого отображаются размер и сложность.

- Пользователь может открыть любой доступный кроссворд.

- Пользователь понимает, какие кроссворды уже решены или находятся в процессе.

---

## US-02 — Начать решение

**Как пользователь**,  

я хочу открыть кроссворд и сразу увидеть игровое поле,  

**чтобы начать решать без дополнительных шагов.**

### Acceptance criteria

- После открытия отображается поле.

- Отображаются подсказки строк и столбцов.

- Игровое поле визуально соответствует размеру кроссворда.

- Не требуется регистрация.

---

## US-03 — Закрасить клетку

**Как пользователь**,  

я хочу закрашивать клетки,  

**чтобы отмечать предполагаемые заполненные клетки.**

### Acceptance criteria

- Tap/click по клетке изменяет её состояние.

- Состояние клетки визуально очевидно.

- Повторное действие позволяет изменить или очистить состояние.

- Изменение происходит без заметной задержки.

---

## US-04 — Поставить крестик

**Как пользователь**,  

я хочу помечать клетки крестиками,  

**чтобы фиксировать клетки, которые не должны быть закрашены.**

### Acceptance criteria

- Доступен отдельный режим крестика.

- Режим можно переключать на мобильном устройстве.

- Крестик визуально отличается от закрашенной клетки.

- Клетку можно очистить.

---

## US-05 — Быстро заполнить несколько клеток

**Как пользователь**,  

я хочу провести пальцем или мышью по нескольким клеткам,  

**чтобы быстро закрашивать последовательности.**

### Acceptance criteria

- Drag поддерживается на touch-устройствах.

- Drag не должен приводить к неожиданному переключению соседних клеток.

- Поведение согласовано с текущим режимом («закрасить» / «крестик»).

---

## US-06 — Продолжить решение позже

**Как пользователь**,  

я хочу закрыть страницу и вернуться к кроссворду позже,  

**чтобы не потерять прогресс.**

### Acceptance criteria

- Прогресс сохраняется локально.

- После перезагрузки состояние восстанавливается.

- Время решения восстанавливается корректно.

- Завершённый кроссворд не теряет статус завершения.

---

## US-07 — Проверить решение

**Как пользователь**,  

я хочу проверить решение,  

**чтобы узнать, решил ли я кроссворд правильно.**

### Acceptance criteria

- Есть явное действие «Проверить».

- При правильном решении отображается успешное завершение.

- При ошибке пользователь получает понятную обратную связь.

- Проверка не уничтожает текущий прогресс.

---

## US-08 — Получить результат

**Как пользователь**,  

я хочу увидеть результат после решения,  

**чтобы понимать, как я справился.**

### Acceptance criteria

- Отображается факт завершения.

- Отображается время решения.

- Есть действие для перехода к следующему кроссворду.

- Есть возможность решить текущий кроссворд повторно.

---

# 7. Функциональные требования

## FR-01. Модель кроссворда

Каждый кроссворд должен содержать как минимум:

- `id`;

- `title` или другое отображаемое имя;

- `width`;

- `height`;

- `difficulty`;

- `rowHints`;

- `columnHints`;

- `solution`.

На первом этапе кроссворды могут быть статическими данными, например JSON-файлами.

Генерация кроссвордов не входит в MVP.

---

## FR-02. Состояния клетки

Клетка должна иметь как минимум три состояния:

1. `empty` — пустая;

2. `filled` — закрашенная;

3. `marked` — отмечена крестиком.

Состояние должно быть однозначно визуализировано.

---

## FR-03. Состояние решения

Для каждого незавершённого кроссворда должно храниться:

- `puzzleId`;

- состояние всех клеток;

- время начала;

- накопленное время решения;

- статус решения.

Возможные статусы:

- `not_started`;

- `in_progress`;

- `completed`.

---

## FR-04. Сохранение

Прогресс должен сохраняться автоматически.

Пользователь не должен вручную нажимать «Сохранить».

Для MVP достаточно локального хранения в браузере, например `localStorage` или IndexedDB.

---

## FR-05. Проверка

Сервис должен уметь сравнивать текущее состояние с эталонным решением.

Минимальный вариант:

- проверить все клетки;

- определить, совпадает ли решение целиком;

- показать результат.

Более детальная подсветка отдельных ошибок не обязательна для MVP.

---

## FR-06. Таймер

Таймер должен:

- запускаться при начале решения;

- отображать прошедшее время;

- корректно восстанавливаться после перезагрузки;

- останавливаться при завершении.

---

## FR-07. Undo / Redo

**Желательно включить в MVP, но допустимо реализовать после основной игровой механики.**

Пользователь должен иметь возможность отменить последнее изменение и вернуть отменённое действие.

Если реализация начинает существенно усложнять MVP, функцию можно перенести в следующий этап.

---

# 8. Mobile UX

Мобильный интерфейс является частью MVP, а не последующей адаптацией.

## 8.1. Основные принципы

- Игровое поле занимает большую часть доступного пространства.

- Не должно быть необходимости использовать мышь.

- Основные действия доступны одной рукой там, где это возможно.

- Клетки должны быть визуально различимы.

- Активный режим должен быть очевиден.

- Ошибочное действие должно легко исправляться.

## 8.2. Режимы ввода

Вместо desktop-модели «левый/правый клик» использовать:

- режим `Закрасить`;

- режим `Крестик`;

- очистку клетки.

Дополнительно можно поддержать:

- drag;

- long press;

- haptic feedback.

Последние три функции не являются обязательными для первой версии.

## 8.3. Размеры

Целевые размеры:

- 5×5 — отлично;

- 10×10 — отлично;

- 15×15 — комфортно;

- 20×20 — полноценный основной сценарий.

Для размеров больше 20×20 можно в будущем добавить zoom/pan.

## 8.4. Orientation

Приложение должно корректно работать:

- в portrait;

- в landscape.

Для больших полей landscape может использоваться как более удобный режим, но приложение не должно требовать обязательного поворота телефона для 20×20.

# 9. Предлагаемая структура интерфейса

## Главная страница

Основной сценарий:

```text

Кроссворды

[ 5×5   Лёгкий     Начать ]

[ 10×10 Средний    Продолжить ]

[ 15×15 Средний    Решён      ]

[ 20×20 Сложный    Начать ]

```

## Страница решения

Основные элементы:

1. подсказки столбцов;

2. подсказки строк;

3. игровая сетка;

4. текущий прогресс;

5. таймер;

6. режим ввода;

7. undo/redo;

8. проверка.

Интерфейс не должен содержать лишних элементов, отвлекающих от решения.

---

# 10. Структура данных

## Puzzle

```text

Puzzle

├── id

├── title

├── width

├── height

├── difficulty

├── rowHints[]

├── columnHints[]

└── solution

```

## PuzzleProgress

```text

PuzzleProgress

├── puzzleId

├── cells[]

├── startedAt

├── elapsedTime

├── status

└── completedAt

```

Разделение важно:

**Puzzle** — неизменяемое описание кроссворда.

**PuzzleProgress** — состояние конкретного пользователя.

# 11. Нефункциональные требования

## Производительность

- Открытие кроссворда не должно сопровождаться заметной задержкой.

- Изменение состояния клетки должно происходить практически мгновенно.

- Ввод не должен зависеть от сетевого запроса.

- Решение кроссворда должно оставаться отзывчивым на мобильных устройствах.

## Надёжность

- Обновление страницы не должно уничтожать прогресс.

- Случайное закрытие вкладки не должно уничтожать прогресс.

- Повреждённое локальное состояние не должно ломать всё приложение.

## Адаптивность

Минимально поддерживаемые сценарии:

- desktop;

- мобильный portrait;

- мобильный landscape.

## Доступность

Минимальный уровень:

- управление с клавиатуры на desktop;

- видимые focus-состояния;

- достаточный контраст;

- состояние клетки не должно передаваться только цветом;

- интерактивные элементы должны иметь понятные подписи.

# 13. Критерии готовности MVP

MVP считается готовым, если выполнены все следующие условия.

## Основной сценарий

- [ ] Пользователь может открыть сайт без регистрации.

- [ ] Пользователь может выбрать кроссворд.

- [ ] Пользователь может открыть кроссворд размером до 20×20.

- [ ] Пользователь видит подсказки строк и столбцов.

- [ ] Пользователь может закрашивать клетки.

- [ ] Пользователь может ставить крестики.

- [ ] Пользователь может очищать клетки.

- [ ] Пользователь может проверить решение.

- [ ] Правильное решение распознаётся как завершённое.

- [ ] Пользователь видит время решения.

- [ ] Пользователь может перейти к следующему кроссворду.

## Сохранение

- [ ] Незавершённый кроссворд автоматически сохраняется.

- [ ] После перезагрузки прогресс восстанавливается.

- [ ] Завершённые кроссворды отображаются как решённые.

## Mobile

- [ ] Все основные действия работают через touch.

- [ ] Нет зависимости от hover.

- [ ] Нет необходимости в правой кнопке мыши.

- [ ] 20×20 можно решить без zoom.

- [ ] Интерфейс работает в portrait.

- [ ] Интерфейс работает в landscape.

- [ ] Drag не ломает состояние клеток.

## UX

- [ ] Новый пользователь может начать решение без инструкции.

- [ ] Основное игровое поле занимает заметную часть экрана.

- [ ] Текущий режим ввода очевиден.

- [ ] Ошибочное действие можно быстро исправить.

- [ ] Нет заметных задержек при взаимодействии с полем.

- улучшенные анимации;

- подсветка завершённых строк и столбцов;

- горячие клавиши;

- haptic feedback;

- более качественная мобильная навигация;

- тёмная тема.

## Этап 3 — Контент

- больше размеров;

- тематические наборы;

- ежедневный кроссворд;

- более разнообразные уровни сложности;

- статистика пользователя.

## Этап 4 — Backend

- аккаунты;

- синхронизация между устройствами;

- серверное хранение прогресса;

- личная статистика;

- рейтинги.

## Этап 5 — Инструменты создания контента

- редактор кроссвордов;

- импорт кроссвордов;

- генератор;

- автоматическая оценка сложности.

---

# 15. Главный критерий успеха

На первом этапе не нужно измерять успех количеством функций.

Главный вопрос:

> **Насколько приятно решить здесь один японский кроссворд?**

Если пользователь может:

**открыть → выбрать 20×20 → начать решать → закрыть → вернуться → закончить → увидеть результат**

без регистрации, непонятных состояний и раздражающего взаимодействия с клетками, то MVP выполняет свою задачу.

Именно **игровое поле и качество его взаимодействия** являются центральной частью продукта. Всё остальное должно подчиняться этому сценарию.
